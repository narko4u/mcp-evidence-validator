# The Empire Labs Agent TRACE record

This directory holds a worked integration sample: an MCP server captured by a
governed agent, appraised, and published as a **TRACE v0.2 Trust Record** that
clears the [agentrust-io](https://agentrust-io.com) conformance suite at
Level 0.

The record is the artifact. Everything below it is the evidence that lets you
check the record rather than believe it.

## What was captured

`secure-filesystem-server` 2026.8.31 (the published
`@modelcontextprotocol/server-filesystem`) was started over stdio. The agent was
shown the served tool menu and chose **one** call from it:

| | |
|---|---|
| tool | `read_text_file` |
| arguments | `{"path": "<allowed-root>/sample.txt"}` |
| outcome | text content returned, `isError: false` |
| declared contract | `sha256:9994016f…` |
| observed contract | `sha256:5b0dc616…` |
| findings | **0** |

`read_text_file` over the deprecated `read_file`, and a read-only tool over
every mutating alternative, because a recorded call should not leave the reader
reasoning about side effects it caused. The full reasoning, including the eight
tools the agent considered and rejected, is committed with the capture at
`examples/captures/agent-directed-directive.json`.

## The identity in the record

```
subject     spiffe://empirelabs.com.au/agent/empire-labs-agent/capture
origin.kind self
origin.producer
            Empire Labs Pty Ltd - Empire Labs Agent (Sovereign)
            / mcp-evidence-validator 0.5.0
model       deepseek / deepseek-flash / DeepSeek-V4.1-Flash
```

Two different things are named here, deliberately.

**The agent is ours.** Empire Labs Agent holds the workload identity, produced
the evidence, and is the producer the record declares. `origin.kind: self` is
the load-bearing value: this runtime produced its own record, rather than
assembling one from governance output somebody else generated.

**The model is not ours.** `model` identifies the reasoning engine, and
`deepseek-flash` (`DeepSeek-V4.1-Flash`) is what the provider's documentation
names. A model field that named an agent would stop identifying a model, and it
is the first thing a reader checks.

The Empire Labs identity inside the model block rides in `model.aibom_uri`,
which points at `examples/agent-directed.mlbom.json`, a CycloneDX 1.7 ML-BOM
naming **Empire Labs Pty Ltd** as the supplier of the Empire Labs Agent, with
the hosted model recorded as a component whose weights are the supplier's and
are not held by us. That is the field the schema provides for describing who
supplied the thing that ran.

## What is claimed, and what is not

Every value in the record is read from an artifact that exists, or computed
from one. Where something is not held, it is absent rather than filled in:

- **`runtime.platform` is `software-only`.** There is no hardware root of trust
  behind this run, so no TDX MRTD or SEV measurement exists to carry.
  `runtime.measurement` is the honest substitute: a documented software
  measurement of the installed workload, recomputable by anyone holding the
  published wheel. For every file in the installed package, in sorted
  relative-path order, fold in the relative path and the SHA-256 of the file's
  bytes, skipping `__pycache__` and `.pyc`. It measures the code that ran. It
  does not measure the host, and it is not an attestation.
- **`build_provenance.slsa_level` is 2, not 3.** GitHub hosted builders with
  Sigstore-signed provenance generated by the build service. Level 3 requires a
  hardened platform; user-defined build steps here run in the same job that
  holds the signing identity, so 3 would be an overclaim.
  `provenance_uri` resolves to the attestation PyPI serves for the exact wheel
  this record's build provenance describes.
- **`build_provenance.provenance_depth` and
  `appraisal.provenance_depth_verified` are both `builder`.** The claim is that
  the build platform generated and signed the provenance; the verified depth is
  the depth we actually ran. With `sigstore` 4.5.0 we verified the DSSE envelope
  signature, the Fulcio certificate chain against Sigstore's published TUF trust
  root, the Rekor inclusion proof, and the signing certificate's OIDC claims
  (issuer, `workflow@ref`, repository, `github-hosted` runner). The script and
  its verbatim output are committed at `examples/verify_sigstore.py` and
  `examples/captures/agent-directed-sigstore-verify.txt`, so the depth is
  checkable rather than asserted. Had any of it failed to verify, the value
  would have stayed at `surface`. It is deliberately **not** `transitive`,
  because we did not resolve the builder's own inputs.
- **The attestation is a PyPI publish predicate, not an SLSA provenance
  statement.** `predicateType` is
  `https://docs.pypi.org/attestations/publish/v1` with a null predicate. What
  supports the SLSA Build 2 claim is the signing certificate: Sigstore-signed,
  generated by the build service, asserting the `github-hosted` runner, the
  workflow, the tag and the commit, logged in Rekor. Level 3 is not claimed,
  because user-defined build steps here run in the same job that holds the
  signing identity.
- **`appraisal.status` is `affirming`, by us.** Our own validator ran the
  declared-vs-observed checks over this execution and returned no findings. It
  is attributed via `appraisal.verifier` and is **not** independent.
- **Neither artifact establishes that the observations captured everything.**
  Verifying this record establishes its signature and the checks actually
  performed. The validator compares the declaration against the observations
  supplied to it. A call that was never recorded cannot be found by comparing a
  declaration to a transcript, so a clean result means the observations are
  consistent with the declaration, and not that they are complete. The ledger
  binds what was observed; it says nothing about what was not.
- **`transparency` is absent.** No SCITT receipt exists for this record, which
  is why the suite stops at Level 0.
- **The workload identity is a namespace we hold by DNS.** We do not run a
  SPIFFE control plane, so no SVID is issued at that path today, and
  `/.well-known/did.json` is not published on the domain. The field is
  well-formed and the trust domain is ours; an issuing control plane is the
  work required to make it more than a name.

## Conformance

```
TRACE Conformance Report -- Level 0 — Software-only
Record : agent-directed-trace-record.json
Digest : sha256:549949b15df85d94ebe5388779e19fe12f169e160534886010f22516303a41cc
  Level 0  PASS
  Level 1  FAIL
  Level 2  FAIL
```

That is the stdout verbatim, including the em dash the suite itself emits in its
verdict string. The summary is one line per level; the module-level reasons live
in the JSON report (`--json conformance.json`), not on these lines.

Level 1 is named **TEE-attested** and fails on hardware, not on code: TR-RTE-001
wants a hardware TEE platform and TR-RTE-004 wants the verifier's expected nonce
bound in. Level 2 is **Transparency-anchored** and additionally requires a SCITT
receipt (TR-ANC-001). Both are infrastructure.

Re-run it yourself:

```sh
pip install agentrust-trace agentrust-trace-tests
trace-tests report --record agent-directed-trace-record.json --max-level 2 \
  --json conformance.json --badge level-badge.svg
```

The suite's own report carries a disclaimer worth repeating: it is a rendering
of one run, it is not signed, and the evidence is the Trust Record identified by
the digest above. Re-run the suite rather than trusting the report.

## Provenance of this sample

The record and the pair it is built from are produced by
`examples/agent_directed_capture.py`, which splits the run so the agent's
decision is a real artifact: phase one writes the served menu, the agent authors
a directive from that menu alone, and phase two executes exactly that directive
and records its digest beside the call. Nothing in the capture fabricates a
call, and the script never picks a tool on the agent's behalf.

To rebuild the record, run the capture, then the ledger:

```sh
mcp-ev-validate validate \
  --declared examples/agent-directed-declared.json \
  --observed examples/agent-directed-observed.json \
  --out evidence.json --head-out evidence.head
mcp-ev-validate verify --ledger evidence.json \
  --expected-head "$(cat evidence.head)"
```

`verify` is the step that matters: it checks the ledger's hash chain against a
head stored outside the ledger, so a ledger that has been edited after the fact
fails there rather than looking intact.
